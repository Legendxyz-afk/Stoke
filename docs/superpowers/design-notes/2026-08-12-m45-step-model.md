# M4.5 — the step-time model, written BEFORE the kernels change

*2026-08-12. Opus 5. Required by the 2026-08-12 ruling's new standing rule:
any "X amortizes Y" premise gets a paper model first. This one is fitted to
M4's measured curve and states falsifiable predictions for B and C, so their
gate runs test the model instead of merely recording a number.*

## 1. The model, and it fits

A static batch step costs a per-token term (compute that every sequence pays)
plus a fixed term (work the step pays once regardless of N — weight streaming,
the parts of the unpack that are weight-only, dispatch):

```
step_time(N) = N·c + f          aggregate(N) = N / (N·c + f)
```

Fitted from the curve's two anchors (N=1 and N=8 medians, quiesced,
3 interleaved cycles):

| | |
|---|---|
| **c** (per-token compute) | **0.112983 s** |
| **f** (fixed per step) | **0.015041 s** |
| f as a share of a 1-token step | **11.75%** |
| asymptote 1/c | **8.851 tok/s** |
| **max batching gain (c+f)/c** | **1.1331×** |
| measured N=1→8 gain | **1.1146×** |

Residuals across N=1..16 are within **±3.3%** (worst: N=16 −3.32%, N=6 −2.69%),
with no trend — a two-parameter fit reproducing sixteen points that closely is
strong evidence the decomposition is the right one.

## 2. What it says, and it corrects my own earlier framing

**The measured 1.1146× is 98.4% of the theoretical 1.1331× ceiling.** The
current batch path is already extracting essentially everything available to
it. So the flat curve is **not** caused by the per-sequence unpack redundancy
in the way I first put it — it is caused by **c dominating f**. Batching can
only ever recover f, and f is 11.75% of a step.

That is a sharper statement than "batching buys nothing because the unpack
repeats", and it changes what each rung is worth:

- **B moves work from c into f.** It cannot do anything else. Its entire value
  is the fraction of c that is weight-only (nibble widening + the 6-bit scale
  unpack) and therefore hoistable out of the per-sequence loop.
- **B does not improve N=1 at all** — at N=1 the work is done once either way.
  The model predicts N=1 stays 7.811 tok/s exactly. **Any measured N=1 change
  from B is a bug or a measurement fault, not a win.**
- **C reduces c itself**, so it lifts every N including N=1. It is the only
  rung that touches the llama.cpp comparison.

## 3. Predictions (falsifiable, recorded before implementation)

Counting the Q4_K AVX2 inner loop by hand, per 8 elements: q4 load+cvt (2) +
mask/shift (1) + q8 load+cvt (2) + `mullo`+`add` (3) ≈ 8 uops, of which the
**weight-only** portion is ~3 (the q4 load, widen and mask), plus the
per-superblock scale unpack amortized at ~0.6. Materialising a widened row and
re-loading it turns 3 into ~2 for sequences 2..N, so the hoistable share of c
is **~15–25%**.

| hoistable share of c | predicted asymptote | predicted N=1 | predicted gain |
|---|---|---|---|
| 15% | 10.41 tok/s | 7.811 (unchanged) | 1.333× |
| 20% | 11.06 tok/s | 7.811 (unchanged) | 1.416× |
| 25% | 11.80 tok/s | 7.811 (unchanged) | 1.511× |

**B's gate reading:** measure the post-B curve, refit c and f from the same two
anchors, and report the hoistable share actually achieved. Landing inside
15–25% confirms the model. Landing below ~10% means the widened-row store/load
ate the saving — record it and proceed to C regardless (C's justification is
N=1, which B never touched).

**The consequence that matters for M5, stated now:** even at the optimistic end,
post-B the asymptote is ~11.8 tok/s against M5's ≥17.7 @ N=8 bar. **B alone
cannot reach M5's bars. C is not optional for them.** The ruling ordered
B → C on risk grounds (B is bit-exact and cheap); this note is why the order
must not be read as "B might be enough".

## 4. Where the model stops

It is a two-term fit, not a first-principles cost model. It does not separate
attention (which grows with context and is not constant per token), the LM
head, or thread-sync overhead — all of those currently sit inside `c` and one
of them may become binding once C shrinks the matvec term. **That is exactly
the ruling's §7.5 attribution ladder, and this note is the reason it exists:
after C, refit and see which term moved.** A rate prediction past C is
therefore not offered here — the uop ratio suggests a large factor, but
llama.cpp reaching 17.45 with essentially C's kernel is the better anchor for
what this box actually allows.
