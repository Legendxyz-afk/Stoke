## 2. The five blockers, in the order they actually fire

Ordered by execution, not by size. **Each is verified, none is expected.**

1. **The tokenizer refuses first**, before the architecture check ever runs:
   `tok: tokenizer.ggml.pre is 'llama-bpe' -- expected 'qwen2'` (`tok.c:691`).
2. **`model.c:657` hard-refuses any architecture but `qwen3`.**
3. **QK-norm is unconditional.** `attn_q_norm`/`attn_k_norm` are fetched per
   layer, passed to `check_norm_tensor()` (`model.c:799-800`) and dereferenced
   at `model.c:1585-6`. Llama has neither tensor.
4. ⚠⚠ **`rope_freqs` appears NOWHERE in `src/`.** Llama-3.2 ships
   `rope_freqs.weight` F32[64] — the per-frequency correction for llama3-style
   RoPE scaling (64 = rope_dim/2). **This is exactly the long-context half of
   B5's own done-when.** Short-context parity can pass with this ignored while
   long context silently diverges: a fixture blind to the defect it exists to
   find.
5. **G=3 is a performance cliff, not a correctness break** — a refinement of
   the sequence doc's hazard. The score loop is
   `for (; g + 4u <= G; g += 4u)` (`model.c:1244`) with a remainder loop at
   `model.c:1282`. At **G=4 the remainder runs zero times** (4 divides 4); at
   **G=3 the 4-wide path runs zero times and the remainder carries 100% of
   attention scoring.** So the fallback does not need writing — it needs
   *proving*, because on Qwen it currently carries none of the load.

## 3. The one number that re-prices this

⭐ **The pre-tokenizer gap is one alternative, not a rewrite — MEASURED.**

`llama.cpp-master/src/llama-vocab.cpp` is on this box. Its active `QWEN2` and
`LLAMA3` regexes, compared by character-level diff (not by eye — two ~100-char
regexes are exactly where a second difference hides):

```
  insert  qwen2[94:94]='' -> llama3[94:99]='{1,3}'
```

**One 5-character insertion at offset 94, and nothing else.** `\p{N}` becomes
`\p{N}{1,3}`: digits group in runs of up to three instead of one at a time.
Same 7 alternatives, same order. stoke hand-implements those 7 at `tok.c:232`,
so this is a change to alternative #3, not a new pre-tokenizer.

⚠ **But the regex is only one of THREE tokenizer deltas, and the other two are
silent.** The same `llama-bpe` branch (`llama-vocab.cpp:2135-2147`) reads:

```
tokenizer_pre == "llama-bpe" → pre_type = LLAMA3; ignore_merges = true; add_bos = true;
```

**(a) `add_bos = true`.** llama.cpp's base default is `false`
(`llama-vocab.cpp:1815`), raised to `true` for the LLAMA3 pre-type. The GGUF
key only overrides it *when present* (`get_key(…, /*required=*/false)` at
`:2557`) — and **Llama-3.2-3B's GGUF has no `add_bos_token` key at all.** So
llama.cpp prepends token 128000; stoke reads
`gguf_meta_i64_or("tokenizer.ggml.add_bos_token", 0)` → **false** → does not.
⚠⚠ **This is a guaranteed token-stream divergence at position 0, it is
completely silent, and it would present as an architecture bug.** Measured
across all three files:

| file | `add_bos_token` | `bos_token_id` | stoke prepends | llama.cpp prepends |
|---|---|---|---|---|
| Qwen bartowski | 0 | 151643 | no | no |
| Qwen unsloth | 0 | **absent** | no | no |
| Llama-3.2 | **absent** | 128000 | **no** | **yes** |

**(b) `ignore_merges = true`.** For LLAMA3, a string already present in the
vocab is emitted directly instead of being run through the merge loop. stoke
applies merges unconditionally. Another silent divergence, and unlike (a) it
does not show up at a fixed position — it shows up on whichever tokens happen
to be whole-vocab entries.

⚠ **What none of this establishes:** that the rest of the tokenizer transfers.
The merges table, the 128k vocab, the special-token set and the chat template
are all different, and M1's 22,848-line unicode sweep is a Qwen artefact
(sequence doc §3.1).

## 3a. B6 is blocked too, on one optional key — and stoke is stricter than its own code

**The unsloth file does not load:**
`fatal: gguf: gguf_meta_i64 -- key 'tokenizer.ggml.bos_token_id' not found`.

Predicted from the metadata diff, then confirmed by running it.

⭐ **The requirement is stricter than the code's own use.** `tok.c:788` reads
`bos_token_id` with the **required** accessor `gguf_meta_i64`, but `bos_id` is
consumed at exactly one place — `tok.c:1101`, under
`if (add_special && t->add_bos_token)` — and `add_bos_token` is read two lines
below at `tok.c:802` with the **optional** accessor `gguf_meta_i64_or(…, 0)`.
So stoke hard-refuses a file over a key it would never read. Both Qwen files
have `add_bos_token = 0`, so on bartowski's file `bos_id` is loaded, validated,
and never used.

The correct idiom is already present two lines from the defect. The fix is to
read it optionally and validate it only when `add_bos_token` is true — which
also has to be reconciled with finding (a), since Llama needs the *default*
raised for llama-bpe.

⚠ **This is a general robustness gap, not an unsloth quirk:** `bos_token_id`
is optional in GGUF and plenty of publishers omit it.

### And the two Q4_K_M files are NOT numerically comparable

All 398 tensor lines are **identical** — same types, dims and `nbytes` — so the
kernel mix is unchanged and performance numbers transfer. **But the weights are
different bits:** the imatrix differs
(bartowski `calibration_datav3.txt` @ **497 chunks**; unsloth
`unsloth_calibration_…txt` @ **79 chunks**).

⇒ **B6 is not "do both files produce the same stream" — they cannot.** It is
"does stoke match llama.cpp *on the unsloth file*". Getting that backwards
would manufacture a BUG-class divergence out of a quantization difference.
The 384-byte file-size delta is metadata only (`general.base_model.*`,
`quantized_by`, `repo_url`, an extra tag, a different `padding_token_id`).

## 4. What this changes about the plan

- B5 was sequenced as "run, grade and gate". **It is an implementation task
  with five named blockers**, and the sequence doc's own framing —
  MILESTONE-risk, not rung-risk — is confirmed rather than softened.
- **B6 was sequenced as "cheap once the file exists". It is blocked too**, on
  one optional key, though the fix is small and the tensor-table result is the
  best possible news for it.
- ⚠⚠ **Three of the defects found this sitting are SILENT** — `add_bos`,
  `ignore_merges`, and `rope_freqs`. None produces an error; each produces a
  wrong answer that looks like someone else's bug. They were found by reading
  the referent's source and diffing metadata, **not** by running anything.
  Had B5 been started by running the model and grading the stream, all three
  would have surfaced as a confusing parity failure with no obvious cause.
- **Item 4 (`rope_freqs`) is the one that can produce a false pass** and it is
  not in the sequence doc's hazard list. It should be graded explicitly at long
  context, not inferred from a short-context green.
- Items 1 and 5 are much cheaper than the doc assumed. Items 3 and 4 are real
  work. Item 2 is a one-line gate plus whatever 3 and 4 require.
- **Nothing here has been built.** No `src/` file was modified this sitting.

## 4a. Both tokenizer predictions CONFIRMED against the real models

`bench/vendor/llama-b10037/llama-tokenize.exe` is a one-shot CLI oracle
(loads, prints, exits — permitted unprompted by
[[ask-before-running-servers]]). Same input, both models:

```
"abc 1234567 def"
  Llama-3.2: <|begin_of_text|> | 'abc' | ' ' | '123' | '456' | '7' | ' def'
  Qwen3   :                     'abc' | ' ' | '1''2''3''4''5''6''7' | ' def'
```

⭐ **Both source-derived claims are now measured, not inferred.** BOS is
prepended for Llama and not for Qwen, from a file carrying no
`add_bos_token` key; and the digit run groups in threes rather than singly.
The order that produced this — read the referent's source, state the
prediction, then measure it — is what made both findings cheap. This pair is
also a ready-made golden for the work below.

## 4b. `ignore_merges` is the expensive one of the three

The `{1,3}` change is four lines in `match_alt3` (`tok.c:308`), and the
`add_bos` default is one line plus a `pre_type` field. **`ignore_merges` is
not**: it needs "is this whole fragment itself a vocab entry?", i.e. a
persistent string→id map — and `tok_from_gguf` builds a `StrMap` only to
`strmap_free()` it at `tok.c:786`. The lookup also has to happen in the
GPT-2 byte→unicode remapped space, not raw bytes.

⚠ **How often it actually changes a stream is UNMEASURED**, and it should be
measured against the oracle rather than assumed: greedy lowest-rank merging
usually reconstructs a whole-word token anyway, so this may be rare — or may
not. Do not implement it on the assumption it matters, and do not skip it on
the assumption it doesn't. `stoke tokenize` + `llama-tokenize` over a corpus
answers it directly.

## 4c. The tokenizer half of B5 is DONE and byte-exact — and `ignore_merges` was measured before it was built

All three deltas are implemented (`dff15c4` for the first two, this commit for
the third). **`stoke tokenize` is now byte-identical to `llama-tokenize` on
Llama-3.2-3B-Instruct** over the 2,078-line multilingual corpus and over the
specials corpus in both modes — three legs, gated by
`tests/tok_llama_golden.sh`, wired into `make test`.

⭐ **`ignore_merges` was NOT implemented on faith.** §4b left the question
open deliberately, and the answer came from running the pre-`ignore_merges`
binary against the oracle and classifying every difference:

| | |
|---|---|
| decoded text | **identical** (108,905 chars both sides) — so every difference was segmentation only |
| ids identical | 28,001 of 28,078 oracle positions (99.726%) |
| stoke SPLIT a token the oracle kept whole | **77** |
| stoke JOINED tokens the oracle split | 0 |
| any other shape | **0** |
| distinct tokens involved | **1** — id 117188 `' مدينة'`, which stoke broke into `[' م', 'دي', 'نة']` |

So it fires, it was the *only* remaining difference, and the whole-fragment
precondition held in every case. The walk is total (0 ids unconsumed on
either side), so nothing was skipped by a resync window.

⚠ **The RATE is corpus-specific and must not be generalised.** 0.548% of the
stream came from one Arabic phrase repeated 77 times by a fixed-seed
generator. "It matters" is established; "it matters 0.5% of the time" is not.

⚠⚠ **The unit fixture is BLIND to one of the two ways this can be got wrong,
and that was proved by mutation, not assumed.** Dropping the GPT-2
byte→unicode remap from the lookup (matching raw bytes instead) leaves
`test_tok.c` at **57/57 green** — its probe token `"zqx"` is ASCII, where the
remap is the identity — and is caught only by the corpus gate, because real
fragments begin with `Ġ`. Six mutations were run in total; two of the first
attempts were **VOID**, not passes: hardcoding the digit bound leaves `pre`
unused, `-Werror` kills the build, and the *stale binary* ran and reported
54/54. The harness now asserts the build succeeded **and relinked** before it
believes any verdict.

⭐ **And a negative result worth more than the positive one: the Qwen goldens
do NOT protect the Qwen path here.** Forcing `ignore_merges = true` for
qwen2 leaves all three Qwen goldens green — including the 22,848-line unicode
sweep. Only the synthetic control (`qwen2_always_runs_the_merge_loop`)
catches it. Greedy lowest-rank merging really does reconstruct the whole-word
token everywhere in Qwen's corpus, exactly as §4b guessed it might — which
means that one tiny test is the only thing standing between a future
refactor and a silent Qwen regression.

## 4d. ⚠ A REAL PARITY GAP THAT IS NOT A BUG: Unicode version skew

`tests/data/unicode_sweep.txt` is the one corpus where stoke and the oracle
still disagree on the Llama file — **one id out of 139,375** — and the cause
is measured on both sides rather than suspected. `tests/gen_unicode_data.py`
predicted this class in writing; this is its first sighting.

- **U+116E2 MYANMAR EASTERN PWO KAREN DIGIT EIGHT** is category **Nd** in
  Unicode 16.0.0, which `src/unicode_data.h` is generated from (Python
  3.14.2). In the table llama.cpp b10037 ships it is **UNDEFINED**
  (`unicode-data.cpp`, the range at `0x116CA`, flags `0x0001`).
- For the input `" <U+116E2>"` the oracle therefore sees *other*, takes alt4
  (`' '?[^\s\p{L}\p{N}]+`) and gets ONE fragment; stoke sees a *number*, so
  alt2/alt3/alt4 all decline the space, it falls through to alt7 and gets
  TWO. **Both are internally correct for their own Unicode version.**
- It becomes visible in the ids only because Llama's merge table carries the
  rule spanning that boundary — `Ġ` + `ð`, **rank 251501 of 280,147**.
  **Qwen's 151,387 merges do not contain it**, and on the identical input
  stoke and the oracle agree exactly on the Qwen model. ⇒
  **`tests/unicode_sweep_golden.sh` has been passing over this same
  classification difference all along** — a fixture blind to a defect it
  covers by name, and the second such case found this sitting.

⏹ **NOT DECIDED, AND DELIBERATELY NOT B5's TO DECIDE.** Closing it means
either hand-editing `unicode_data.h` to mirror one vendored oracle build's
Unicode version (which the generator's docstring sanctions, but which makes
the table a snapshot of a snapshot and inverts the moment llama.cpp
regenerates theirs) or accepting that stoke targets current Unicode and
diverges from older oracle builds on newly-assigned codepoints. `tok.h`'s
contract currently says byte-exact against b10037, so today the contract and
the code disagree on this one codepoint. **The Llama gate therefore covers
the two natural-text corpora and NOT the sweep** — no red gate, no pretending.

## 4e. ⚠⚠ THERE IS A SIXTH BLOCKER, AND §2's LIST MISSED IT: THE ROPE TYPE

§2 enumerated five blockers "in the order they actually fire" and called each
one verified. **It is six.** Llama-3 does not use the rotary pairing stoke
implements, and nothing about that fires as an error.

- `llama.cpp`'s `llama_model_rope_type()` returns **`LLAMA_ROPE_TYPE_NORM`
  for `LLM_ARCH_LLAMA`** and **`LLAMA_ROPE_TYPE_NEOX` for `LLM_ARCH_QWEN3`**
  (`llama-model.cpp:1329`/`:1367` against `:1386`/`:1439`).
- NORM rotates **adjacent** elements `(2k, 2k+1)`; NEOX rotates
  `(k, k+head_dim/2)`. Same angles, same theta chain, different pairing —
  ggml builds ONE cache and both read it, differing only in
  `rotate_pairs(n_dims, 1, ..., scale=1)` versus
  `rotate_pairs(n_dims, n_dims/2, ...)` (`ggml-cpu/ops.cpp:5934-5950`,
  `6069-6077`).
- The conversion script permutes Q/K on the way into a llama GGUF precisely
  so the adjacent pairing is correct for the stored weights.

⚠ **This is stoke's own recorded TRAP #3, arriving from the other side.**
`kernels.h`'s existing `rope_neox` comment warns that the adjacent pairing
"produces plausible-looking garbage here" — the warning was written for
someone reaching for GPT-J style on Qwen, and the symmetric mistake (NEOX on
Llama) is equally silent. A short-context smoke test on a 3B model would have
produced *fluent text* either way, which is why this had to come from reading
`llama_model_rope_type()` rather than from running the model.

⭐ How it is graded: `rope_norm` against `rope_neox` by an **exact
permutation equivalence** — de-interleave the vector, run the
already-trusted NEOX kernel, re-interleave, and require bit-for-bit
equality. No golden constant, no tolerance, and a `rope_norm` that pairs
`(k, k+half)` fails it immediately. A second test repeats it with
`freq_factors` non-uniform, because the factors are indexed by PAIR in both
kinds and an element-indexed version passes the first test.

⏹ **Method note worth keeping: §2's five were found by reading the loader
and the file. The sixth was only findable by reading the REFERENT'S
architecture dispatch.** "Which blockers exist" was itself scoped by where
the previous sitting looked.

## 4f. A correction to §3's characterisation of `rope_freqs`

§3 item 4 says `rope_freqs` means "short-context parity can pass with this
ignored while long context silently diverges". **That is not quite right,
and the file says so.** `rope_freqs.weight` was read out of
Llama-3.2-3B-Instruct: 64 f32 values running **1.0 to 32.0, with only 29 of
the 64 equal to 1.0**. The correction divides `theta_k` at EVERY position,
not only large ones — the magnitude simply grows with position, because
`theta_k` itself does.

So the fixture is not blind to it at short context; it is only *weakly*
sensitive there (at pos 1 the affected angles differ by ~1e-6, which may not
move an argmax). The operative warning survives with a better reason: grade
long context **explicitly**, because a short-context green is a WEAK signal
here, not a null one. The exact formula was read out of ggml rather than
inferred — `rope_yarn(theta/ff, ...)` with `theta *= theta_scale` after, so
**the division is at USE and the accumulator is untouched**; folding it into
the accumulation would compound it across k.
