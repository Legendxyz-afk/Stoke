# M5 entry — the traffic budget, the entry rungs, and the asserted set

*2026-08-19, Opus 5. Written at M5 entry, before any M5 code, per the
ROADMAP's M5 row ("M5's design note MUST record the chunk-alignment
invariant"). Binds: the chunk-alignment invariant (§1), the asserted set
(§2), the entry-rung order (§4), the `ATT_LANES` disposition (§5). Records
as a direction check, Kabir overrules: the Q8-KV default (§6).*

**What is new here and is not a restatement:** §3 recomputes the 08-11
bandwidth budget against the engine that actually exists, and the budget's
crossover turns out to describe a *different* engine — one that neither
re-reads a KV head per q-head nor stores KV at f16. Stoke's real crossover is
**2,117** token-positions, not 16,936. That single correction reorders M5's
work: the KV-read restructure (§4, rung E2) stops being an optimisation and
becomes the thing that puts the N=16 bar inside the physical envelope at all.

---

## 1. The chunk-alignment invariant (ROADMAP-mandated)

**S-ALIGN — a prefill chunk ends on a block boundary, or the prefix cache
cannot register what the chunk produced.**

Prefix dedup registers *whole* blocks: `bp_dedup_find` is keyed on a chained
hash over exactly `BP_BLOCK_TOKENS` ids, and `kv_adopt_prefix` walks whole
blocks from ordinal 0 (`src/kv.c:144-161`). A chunk that stops mid-block
leaves that block partially written and unregistrable; the next chunk fills
it, and until then the sequence's own prefix is invisible to every other
sequence. Chunk 128 / block 16 satisfies this by construction (128 = 8×16),
so today the invariant costs nothing — which is exactly why it has to be
written down. **A future chunk change must re-check it**, and so must any
change to `BP_BLOCK_TOKENS`. Mined from the vLLM v1 scheduler 2026-08-12;
the ROADMAP's M5 row carries the mandate.

Asserted form, checkable at every chunk boundary: `chunk_end % BP_BLOCK_TOKENS
== 0` for every chunk except the one that ends the prompt.

## 2. The asserted set

M5's sim asserts **M4's structural set unchanged** — I1–I11, enumerated in
`2026-08-11-m4-invariants.md` §2.3 — **plus the scheduler set below.** Cite
the set, never the count: that note's own recommendation, and M4's "11
invariants referenced by count in three documents and listed in none" is the
sixth instance of this milestone's signature failure mode.

| | invariant | what its violation looks like |
|---|---|---|
| **S1** | at most one request holds PREFILLING | two prefills co-run, ITL collapses, and nothing in the output says so |
| **S2** | admission only when `free_blocks ≥ blocks(prompt) + W`, `W = max(8, 2·\|RUNNING\|)` | livelock: everything admitted, nothing able to take its next decode block |
| **S3** | WAITING is drained FCFS, except a preempted request pushed to the FRONT | starvation of the oldest request — the property the LIFO victim rule exists to give |
| **S4** | the preemption victim is the YOUNGEST RUNNING | as S3: the oldest is never preempted, which with finite work is starvation-freedom by induction |
| **S5** | every runnable decode decodes every step (a chunk co-runs, never displaces) | the ITL guarantee's skeleton; a displaced decode is a stall no percentile explains |
| **S6** | preempt-replay losslessness: outputs equal the same trace against an infinite pool | silent: a re-prefill that re-samples instead of replaying recorded ids diverges only sometimes |
| **S7** | S-ALIGN (§1) | prefix cache silently stops hitting; throughput drops with no incorrect output |
| **S8** | cancellation-safety (Fable 08-02): abort in ANY state frees every block, refcounts stay consistent (I1–I3 continue to hold), and the remaining schedule does not stall | M6's client-disconnect path — find it here, not there |

S8 is teardown (already I1–I3) *plus* a scheduler property; only the second
half is new, and it is the half M6 needs. Recorded, not gated: preemption
count per trace (thrash metric) and p95 request-completion latency under the
mixed trace.

## 3. The traffic budget, recomputed against the engine that exists

Geometry read from the GGUF, not recalled: `n_layer=36`, `n_head=32`,
`n_head_kv=8` (GQA 4:1), `head_dim=128`. Model 2,497,280,736 B (Q4_K_M).
W = 43.6 GB/s (Q4_K_M at 6T, re-measured 2026-08-11; the file's ceiling is
44.8 at 10T).

**Bytes of K+V per position, all layers and kv-heads:**

| representation | per (layer, kv_head, pos) | per position |
|---|---|---|
| f32 (default) | 1,024 B | **294,912 B** |
| f16 (the 08-11 budget's assumption) | 512 B | 147,456 B |
| Q8_0 (`--kv q8`) | 272 B | 78,336 B |

**But that is what a position *costs to store*, and the budget priced
storage. What decode *reads* is a different number, because every q-head
re-reads its kv-head's K and V independently** (`att_heads_run`,
`src/model.c:942-984`: the loop is q-head-outer, and `kv_read` is called once
per (q-head, position) in the score pass and again in the value pass). With
GQA 4:1 that is a **4× read amplification over storage**:

| | read per token-position | crossover N×L where KV = weights |
|---|---|---|
| **stoke today** (f32, q-head-outer) | 1,179,648 B | **2,117** |
| after E2 (f32, kv-head-outer) | 294,912 B | 8,468 |
| the 08-11 budget's engine (f16, no amplification) | 147,456 B | 16,936 |
| after E2 + `--kv q8` | 78,336 B | 31,880 |

**⚠ THE 08-11 BUDGET'S CROSSOVER IS NOT WRONG — IT IS ABOUT AN ENGINE STOKE
IS NOT.** 2,497,280,736 / 147,456 = 16,936 reproduces exactly, so the
arithmetic stands; it prices f16 storage read once. Stoke reads f32 four
times. **The structural claim the ROADMAP calls "the live constraint" is
therefore stronger than it was stated, by 8×**: M5 does not merely become
KV-dominated somewhere out at N=16/L=1059 — at N=8 with a 1,500-token context
it is at 12,000 token-positions against a crossover of 2,117, i.e. **KV traffic
is already 5.7× the weight traffic.**

**The check that makes this more than arithmetic — and it is sharper than a
totals comparison, because L4 measured the CURVE, not a point.** L4 reports
decode at ctx 1500 as **106.75 ms/token** with a slope of **0.0289
ms/context-token**. Split it:

| | measured | what traffic predicts | ratio |
|---|---|---|---|
| **intercept** (weights + the rest) | 106.75 − 0.0289×1500 = **63.40 ms** | 2.4973 GB ÷ 43.6 GB/s = 57.28 ms | **90.3% of ceiling** |
| **slope** (per context-token) | **0.0289 ms** | 36×32×1024 B = 1.1796 MB ÷ 43.6 GB/s = 0.02706 ms | **93.6% of ceiling** |

**Both halves of the measured curve are bandwidth-bound, independently, to
within 10%.** The slope term is the 4× amplification made visible: it is
computed from `n_head`, not `n_head_kv`, and it lands within 7% of measurement.
That is a much stronger statement than "the totals agree" — the totals could
agree by two errors cancelling, whereas a slope and an intercept derived from
different byte counts agreeing separately could not.

**What this does to the bars.** Aggregate ceilings at L=1500, W=43.6, traffic
only (upper bounds — no compute, no scheduler, no stall):

| | N=8 ceiling | vs the 17.7 bar | N=16 ceiling | vs the 16.8 bar |
|---|---|---|---|---|
| **today** | 20.9 tok/s | **1.18× slack** | 22.6 tok/s | **1.35× slack** |
| after E2 | 57.8 tok/s | 3.27× | 72.9 tok/s | 4.34× |
| after E2 + q8 KV | 101.5 tok/s | 5.7× | — | — |

**A bar at 85% of a traffic ceiling is not a bar, it is a physics claim.** No
engine runs at 85% of pure DRAM traffic with a scheduler, sampling and a
prefill chunk in the loop; stoke's own best measured figure is 92% of ceiling
at N=1 with *nothing* else running. **⇒ Rung E2 is not an optimisation. It is
the difference between M5's bars being reachable and being arithmetic.** This
supersedes nothing in the retired 08-17 alarm — that alarm was about a
single-threaded attention loop and is correctly retired — but it names a
second, independent reason the bars were at risk, and this one is structural
rather than a measurement artefact.

## 4. The entry rungs

The three items L4 explicitly did not fix, reordered by §3 and by what
enables what. Each lands behind the **byte-compare gate** (§4.4), because
each claims bit-exactness by an argument, and an argument of that shape is
worth exactly the byte-compare that checks it.

### E1 — hoist the KV write phase out of the sequence loop; one dispatch per layer

Today `forward_batch_body` runs a sequence-outer block (`src/model.c:1057-1122`)
that per sequence does QK-norm → rope → `kv_note_token` → `kv_write` → **a
`pool_for_units` dispatch over that sequence's q-heads**. At N=16 that is
16 dispatches × 36 layers = **576 broadcasts, wakeups and joins per token**,
where 36 would do.

Split the block in two: phase 1 (per sequence: QK-norm, rope, note, write),
phase 2 (one dispatch over the flattened `n_seq × n_head` unit space).

**Why the split is safe, stated as the thing that could make it unsafe:** the
hazard is a write landing in a block another sequence is concurrently reading.
It cannot. Adoption is admission-time only and whole-block only
(`kv.h:102`, `kv.c:142`), so a sequence writes only into blocks it alone owns —
its adopted prefix blocks are full and never rewritten, and decode never
revisits a position. **This is the claim to attack first if the byte-compare
moves.**

**Bit-exactness:** phase 2 reassociates nothing — each (sequence, q-head)
computes the same sums in the same order into its own slice of its own
`s_attn_out`. Phase 1's reordering is across sequences, whose scratch is
disjoint by construction (the interleaved-identity test exists for exactly
this).

**Predicted gain: dispatch overhead only.** A dispatch is a few µs; 540
saved dispatches × ~3 µs ≈ 1.6 ms against a ~140 ms N=16 step ⇒ ~1%. **Priced
at half: negligible.** E1 is on the list because it is E3's *enabler*, not for
its own number — and saying so now is the guard against later crediting it
with E3's win.

### E2 — kv-head-outer attention: remove the 4× GQA read amplification

Restructure `att_heads_run` from q-head-outer to **kv-head-outer**: one unit =
one kv-head; load `K[j]` once and take `gqa_group` dot products against it;
after `gqa_group` softmaxes, load `V[j]` once and accumulate into
`gqa_group` outputs.

**Bit-exactness:** every dot product is still `for d: a += q[d]*k[d]`, left to
right, which is character-for-character `vec_dot_f32` (`src/kernels/vec.c:11`);
every V accumulation is still ordered over `j`. What changes is *which loop is
outer* and *how many times a byte is fetched* — not one addition's operands or
order. Parallelism is still over independent outputs, so no twin, no grading
run, no re-anchor (the L4 argument, unchanged).

**Predicted gain — as a CURVE, which is what makes it refutable.** E2 divides
the slope's byte count by `gqa_group`: 1.1796 → 0.2949 MB per context-token.
Carrying the *measured* 93.6% slope efficiency forward rather than assuming
ceiling, the slope goes **0.0289 → 0.00722 ms/context-token**. The intercept is
untouched — E2 moves no weight bytes.

| avg ctx | today | predicted after E2 | argued | **priced at half** |
|---|---|---|---|---|
| 87 | 65.9 ms | 64.0 ms | 1.03× | 1.015× |
| 554 | 79.4 ms | 67.4 ms | 1.18× | 1.09× |
| 1500 | 106.75 ms | 74.2 ms | **1.44×** | **1.22×** |

**The halving is the standing rule, three instances deep** — L4 predicted
317→63 and measured 106.75; A′ 0.907×; Q6_K 1.108× against 1.20×.

**⚠ THE CURVE IS A BETTER TEST THAN THE HEADLINE RATIO.** E2 removes a term
*proportional to context* and touches nothing constant, so the gain must be
~1.0× at ctx 87 and grow. **A large, flat gain across contexts would refute the
mechanism even while looking like a win** — it would mean the speedup came from
somewhere the argument does not name, and the argument is what the next rung
gets built on.

**Cost:** the per-worker scores scratch grows from `max_ctx` to
`gqa_group × max_ctx` floats (4,096 → 16,384 floats = 64 KB per worker; 8
workers = 512 KB). **The unit count drops from `n_head`=32 to `n_head_kv`=8**,
which at N=1 is 8 units over 6–8 workers — one each, and an E-core straggler
now holds a 4× larger claim. That is a real balance regression at N=1 and the
reason E1 (which flattens `n_seq × n_head_kv`) matters at N>1. Measure it;
do not argue it.

### E3 — batched prefill

Prefill is position-by-position: every position re-streams all 2.4973 GB of
weights. llama batches at `ubatch` 512. `matvec_batch` already applies each
weight once per layer across a batch, and `forward_batch_body` already takes
N "sequences" — so a prefill chunk is that body run with the chunk's positions
as its rows, **all sharing one `Kv` handle** (they are one sequence; the
one-handle-per-sequence rule in `kv.h:12` is about *distinct* sequences and is
not violated).

**E1 is what makes this correct rather than delicate.** With the write phase
hoisted, all of the chunk's K/V is resident before any of the chunk's
attention runs, so position *p* attending over `0..p` picks up its chunk-mates
at positions `< p` naturally — **intra-chunk causality holds by construction**,
with no mask and no special case. In today's interleaved order it would depend
on the sequence loop's order, which is exactly the kind of correctness that
holds until someone reorders a loop.

**Predicted gain:** prefill only, and large — the weight term amortises across
the chunk. Not priced here: prefill is not on the decode bars, and E3's number
belongs to the ITL and p95 measurements, not to the aggregate throughput bar.
Chunk = 128 (S-ALIGN §1); 512 would also be block-aligned if the bench
justifies it.

### 4.4 The gate every rung lands behind

`tests/tooling/run_att_par_verify.ps1`'s protocol, retargeted: every arm
byte-compared **against an archived binary**, never against another arm
(agreement among new arms is also consistent with all of them being wrong
together — the L4 lesson). Axes that must stay: **`--kv q8` is mandatory, not
optional** (at f32 `kv_read` is zero-copy and never touches the per-worker KV
scratch, so an f32-only check cannot see a buffer that is too small or shared;
that is precisely how the 4-lane loop's 3,072-byte overrun survived review),
two thread counts, ≥2 prompt lengths, and the binary-newer-than-source guard.

**A referent must be archived first.** No `stoke-m45-gate-*.exe` exists —
M4.5 closed against `stoke-m45-maddubs-f3b7181a.exe` (pre-L4). M5's rungs
change the L4 loop, so the m45 binary itself becomes the referent and must be
archived at M5 entry, before the first edit.

## 5. `ATT_LANES` — deleted by E2, not benchmarked against it

`ATT_LANES=4` runs four *positions* of one q-head as four independent FP
chains. E2 runs four *q-heads* against one position — also four independent
chains, saturating the same ~4-cycle FP add latency, while additionally
fetching the K vector once instead of four times. **E2 subsumes it.** Keeping
both would mean 16 live chains and 16 KV scratch slots for no argued reason.

Disposition: `ATT_LANES`, `g_att_lanes`, `STOKE_ATT_LANES` and
`ATT_KV_FLOATS`'s `ATT_LANES` factor are **deleted as part of E2** — a
code-deletion change riding E2's byte-compare, not a separate perf change.
It earns ~1.3% (L4 isolation: lanes alone 1.26×, pool alone 2.90×, both
2.94×), so there is nothing to protect. `STOKE_ATT_CHUNK` stays: it becomes
the knob over kv-head units, and its own header already anticipated E2
("a chunk of gqa_group reads that head's K and V once instead of four times —
which is worth measuring, not assuming"). E2 is that, made structural instead
of hoped-for from cache residency.

## 6. The Q8-KV default — direction check, Kabir overrules

`stoke/MEMORY.md` (2026-08-12) parked this call here: *"f32 KV stays the
default; M5's design note carries the dtype call."*

**Decision: f32 stays the default. `--kv q8` is documented as the answer to
RAM, not to speed.** Three reasons, in order of weight:

1. **After E2, Q8-KV is not needed for the bars.** N=8 slack goes 3.27× → 5.7×;
   the bar was never the binding constraint once the amplification is gone.
   Buying 1.7× more headroom we do not need, at the price below, is a bad
   trade.
2. **The price is measured, not hypothetical:** M4 gate item [4] found
   38/50 prompts diverging at 1.1875 %/token — zero BUG-class, all
   ARITHMETIC-CLASS, dispositioned as a results-vs-physics memo. That is fine
   for a flag and expensive for a default.
3. **The headline bars should land on the arithmetic every parity artifact was
   made against.** f32 is that; a Q8-KV headline would mean the product gate
   and the correctness lineage no longer describe the same binary.

**Where Q8-KV does earn its default-adjacent status: capacity.** Admission is
full-reservation (I8), so a pool for N sequences reserves `N ×
kv_blocks_for_ctx(ctx)` regardless of sharing. At N=16, ctx 1500, f32 that is
1,504 blocks × 4.72 MB = **7.1 GB of pool against a 2.5 GB model (≈9.6 GB)**;
at Q8 it is 1.88 GB (**≈4.4 GB**). **M5's memory-pressure trace is where this
is demonstrated, and the honest statement is that `--kv q8` is what makes
N=16 at long context fit on a 16 GB box** — a capacity claim, with a stated
divergence cost, not a throughput claim.

## 7. Deliberately deferred, with its number attached

**Prefix-shared attention batching.** Under the agentic trace, N sequences
share a 1–2k prefix. Dedup shares its *storage*; every sequence still *reads*
it independently, so the shared prefix is fetched N times per token. Batching
sequences inner over the shared leading blocks would cut that by N — at N=8,
ctx 1500, all-shared, on top of E2: 2.94 → 0.44 GB of KV per step, i.e. the
step becomes weight-dominated again and the ceiling goes 57.8 → 118.7 tok/s.

It is bit-exact by the same independent-outputs argument as E2. It is deferred
because it needs the block tables of several sequences walked together — a
real structural change — and §3 says the bars clear at 3.3× slack without it.
**Recorded here so it is a decision and not an oversight**, and so the next
session finds the number rather than re-deriving it.
