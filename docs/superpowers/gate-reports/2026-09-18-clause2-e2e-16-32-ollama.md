## 4. Block 2 — @32, the "N > 16" question — and the server it found

### 4.1 Attempt 1 (11:19–11:38, binary `02211d65`): 13 of 32 clients refused

The first llama unit ran clean (337.4 s, `n_slots 32`, **`n_ctx_slot 768`** —
llama-server pads the per-slot context up to a multiple of 256, so 22528/32 =
704 is served as 768, total 24,576: capacity in llama's favour, no work
difference, and the §6 tripwire "ctx/slot ≠ 704" was a mis-derived constant,
not a void; the summariser now knows the padding). **The first stoke unit
failed: clients 19–31 got `WinError 10061 — actively refused` at connect; 19
were admitted.** Killed at Kabir's word, diagnosed without a model server:

- `src/server.c` listened with a **backlog of 16** and accepts **one
  connection per turn**; once a prefill is running a turn is a whole
  256-token chunk step (~2.8 s).
- `tests/tooling/backlog_probe.py` (pure sockets): Windows DROPS a SYN that
  finds the queue full, the client retransmits at ~1 s and ~2 s and then
  reports "actively refused" — so a queue drained at decode speed (70 ms
  turns: 40/40 through a backlog of 16) never shows it, and one drained at
  prefill speed does: **backlog 16, 32 clients, 2.8 s per accept → 17
  accepted, 15 refused at 2.0 s; backlog 48 → 32/32, last accept at 81 s.**
  The sitting's 19 = 16 queued + the three accepted before generation began.
- ⚠ The first two cuts of `tests/tooling/burst_smoke.py` were BLIND — one
  burst during decode, one sent a prompt longer than `--ctx` that the server
  refused before it entered prefill — and read 30–40/40 on the broken binary.
  Made red first: on the backlog-16 binary it answers 16 and refuses 14; on
  the fix, 30/30.
- Fix `b1ee6b3`: backlog 16 → `MAX_CONNS` (one constant; no effect below 17
  simultaneous connections, so blocks 1/3/4 stand). The one-accept-per-turn
  loop is unchanged: with the queue `MAX_CONNS` deep the last of a 32-burst
  is accepted ~30 turns in, still ahead of its own prefill turn, so it costs
  no throughput; draining the queue per turn is a follow-up with its own A/B.

⚠ `MAX_CONNS 48` was necessary and not sufficient, and the pre-flight that
found the first did not find the second because it read the connection
TABLE and not the listen QUEUE — the same enumeration trap as fixture #14: a
list of blockers is scoped to which sources were read.

## 5. Disposition

- **Clause 2's llama half is now PASSED at both of the clause's widths: 1.181×
  @8 (09-15, 5/5 pairs) and 1.195× @16 (3/3 pairs), same lineage, the same
  ~4% sitting-to-sitting noise well inside the margin.** The ROADMAP M7 row and
  Phase-1 paragraph move.
- **Clause 2's ollama half MISSES ≥ 2.0× at both widths, 1.735× and 1.836×,
  exactly as pre-registered and for the reason pre-registered**: a serial
  ollama does 8 or 16 prefills of the same size stoke does, and prefill is the
  bulk of both walls. Recorded as a documented miss (ROADMAP row; SEQUENCE I.5
  row [2]) — **not re-fitted**. What would meet it: the scheduler overlap item
  (SEQUENCE IV.6 row 1 — decode rows no longer waiting for a chunk's whole
  step, which also retires the clause-4 stall), or a cheaper prefill; both are
  Phase 1.5 work by the 09-16 ruling. Alternatively the clause's referent is
  mis-specified — `ollama-default` on a CPU box is a one-slot server and
  "≥ 2× a serial server" is a statement about prefill cost, not concurrency;
  that is Kabir's call, not the code's, and the number stands either way.
- **Clause 4's re-anchor is CLOSED with the referent's own number**: llama-server's
  client-observed ITL max @16 is 29 s (three units, 28.8–29.9), the memo's
  "stalls the same way" holds, and the memo's §5 "owed" line is closed with it.
- **@32 (not a clause): 1.281×, 3/3 pairs, above @16** — Kabir's "are we
  ahead past 16" is answered yes, by more, and the pre-registered mechanism
  bet survives its falsification test. H8 (TTFT p50 ratio) missed below its
  band @32 and is recorded as such.
- **H6's cadence sub-claim missed** at both widths: stoke's ITL p50 is 311 ms
  @16 and 556 ms @32, not inside 250 ms (llama-server's: 393 / 813 ms).
  Recorded; gate [3] is already a documented miss on the same mechanism.
- **Two `src/server.c` constants changed during the sitting, both Kabir's
  call, both verified red-then-green and suite-green before any unit ran on
  them: `MAX_CONNS` 24 → 48 (`9eca59e`, the pre-registered decision) and the
  listen backlog 16 → `MAX_CONNS` (`b1ee6b3`, found by the first @32 unit).**
  Neither can touch an N ≤ 16 unit, so blocks 1/3/4 stand on `9eca59e`; the
  WSL matrix on `b1ee6b3` runs after this report. The freeze (SEQUENCE 4.1)
  follows that matrix.
- Follow-up, not for this sitting: drain the whole accept queue per server
  turn (a TTFT nicety for bursts, not a throughput item); the harness could
  track ollama's runner child so its CPU-seconds are readable.
